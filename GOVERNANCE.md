# 🏛️ Project Governance

## Project stewardship
This repository is maintained by its owner. The maintainer is responsible for prioritizing issues, reviewing contributions, deciding releases and coordinating security reports.

## Decision process
- Small fixes may be reviewed directly by the maintainer.
- Significant architecture, data model, authorization or dependency decisions should include a written rationale and, where useful, an ADR.
- Security-sensitive changes require explicit review of the threat model and affected tests.
- User-facing features should include acceptance criteria and accessibility/privacy considerations.

## Contributions
Contributors may open issues and pull requests under the root [CONTRIBUTING.md](CONTRIBUTING.md). A pull request is not accepted solely because CI passes; the maintainer reviews correctness, security, maintainability and project fit.

## Maintainer authority
The maintainer may defer, request changes, close or reject contributions that are out of scope, unsafe, unmaintainable or inconsistent with project goals. Decisions should be explained respectfully when practical.

## Conduct and security
All participants are expected to follow [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md). Vulnerabilities must be reported privately using [SECURITY.md](SECURITY.md), not a public issue.

## Changes to governance
Material governance changes should be documented in the repository history and summarized in CHANGELOG.md.
